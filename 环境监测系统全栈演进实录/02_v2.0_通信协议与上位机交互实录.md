## 2. UART 物理帧与微秒级传输开销推演

### 2.1 物理帧结构（115200 8-N-1）
```text
电平
高 ──┐                                   ┌────── (回到空闲态)
     │       0   1   2   3   4   5   6   7   │
低   └───┴───┴───┴───┴───┴───┴───┴───┴───┘
      起始位       8 位数据位 (LSB先发)      停止位
     (低电平)                                (高电平)
     |<──────────────── 10 个 Bit ──────────────>|
```

- **空闲电平**：默认保持高电平；
- **起始位（Start Bit）**：1 位低电平（制造下降沿供接收端硬件波特率时钟同步）；
- **数据位（Data Bits）**：8 位有效载荷（**LSB 低位先发**，与 I2C 的 MSB 先发正好相反）；
- **校验位（Parity）**：`N`（无校验）；
- **停止位（Stop Bit）**：1 位高电平。
- **单字节物理开销**：传输 1 个有效字节，线路上跑了 **$1 + 8 + 0 + 1 = 10 \text{ 个 Bit}$**。

### 2.2 时延与吞吐量数学计算
- **传输 1 个 bit 的时间**：
  $$t_{\text{bit}} = \frac{1}{115200} \approx 8.68 \ \mu\text{s}$$
- **传输 1 个完整字节的时间**：
  $$t_{\text{byte}} = 10 \times t_{\text{bit}} \approx 86.8 \ \mu\text{s}$$
- **串口的理论最大物理吞吐量**：
  $$\text{Throughput} = \frac{115200}{10} = 11520 \text{ 字节/秒} \approx 11.25 \text{ KB/s}$$
- **发送单帧（9 字节）的总耗时**：
  $$T_{\text{frame}} = 9 \times 86.8 \ \mu\text{s} \approx 781.2 \ \mu\text{s} \approx 0.78 \text{ ms}$$

## 3. 定长 9 字节二进制协议帧设计美学

```
┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
│ 0xAA │ 0x55 │ 0x01 │ Temp_H Temp_L │ Humi_H Humi_L │  CS  │ 0x0D │
└──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
 Byte 0 Byte 1 Byte 2  Byte 3 Byte 4  Byte 5 Byte 6  Byte 7 Byte 8
 [ 双字节帧头 ]  [类型]   [ 原始温度 ]   [ 原始湿度 ]  [校验和] [帧尾]
```

### 3.1 协议字段拆解与设计考量
1. **双字节特征帧头（`0xAA 0x55`）**：
   - 二进制分别为 `10101010` 与 `01010101`，属于剧烈交织的高低电平交替码，物理抗干扰识别度极高；
   - 相比单字节帧头，双字节连在一起在环境数据中偶然碰巧出现的概率低于 $\frac{1}{65536}$，提供强同步保障；
2. **数据类型字段（`0x01`）**：
   - 预留扩展空间，便于后续版本无缝扩展气压帧（`0x02`）或报警帧（`0xFF`）；
3. **定点化传输（Fixed-Point）**：
   - **温度（`int16_t`）**：放大 10 倍（$25.4^\circ\text{C} \to 254$），支持负温（$-12.5^\circ\text{C} \to -125$）；
   - **湿度（`uint16_t`）**：放大 10 倍（$60.5\% \to 605$）；
4. **校验和（Checksum）**：
   - $\text{Checksum} = (\text{Byte2} + \text{Byte3} + \text{Byte4} + \text{Byte5} + \text{Byte6}) \ \& \ 0\text{xFF}$；
5. **帧尾（`0x0D` / `\r`）**：
   - 辅助作为状态机的闭合校验。

### 3.2 为什么坚决杜绝直接传输 `float` 浮点数？
1. **节省 50% 带宽**：float 占用 4 字节，温湿度需 8 字节；定点数仅需 4 字节；
2. **杜绝跨平台解析偏差**：IEEE-754 标准在特定低成本 MCU 或 DSP 平台可能因尾数截断造成微小误差，整型二进制的原码/补码定义全局唯一；
3. **消除 FPU 算力消耗**：STM32F103 无硬件浮点单元，整型位移（`>> 8`）仅需 1 个时钟周期，避免调用庞大的软浮点计算库。

## 4. 大小端序（Endianness）与字节切分深水区

### 4.1 大小端模式区别与 STM32 内存布局
- **小端模式（Little-Endian）**：低位字节存放在低地址（“小端低低”）。**ARM Cortex-M 默认采用小端**；
- **大端模式（Big-Endian）**：高位字节存放在低地址。**网络通信协议统一规定为大端序**。
- **实战举例**：温度 $-20.0^\circ\text{C}$，放大 10 倍为 $-200$，其 16 位补码为 `0xFF38`：
  - 在 STM32 内存中：低地址存放 `0x38`，高地址存放 `0xFF`；
  - 在物理串口线上传输时：按照大端序先发高字节 `0xFF`，后发低字节 `0x38`。

### 4.2 为什么缓冲区必须声明为 `uint8_t` 而绝不能用 `int8_t`？
这是很多 C 语言学习者最容易踩中的**符号位扩展灾难**：
1. **`uint8_t` 的本质**：它代表物理世界的**原始纯字节容器（Raw Byte Container）**，无任何正负属性；
2. **若误用 `int8_t` 的后果**：高字节 `0xFF` 在 `int8_t` 视角下会被解释为 `-1`。在后续执行累加校验和 `sum += tx_frame[i]` 时，C 语言会触发整型提升（Integer Promotion），符号位被强制扩展为 32 位全 1 的 `0xFFFFFFFF`，导致校验和运算全部崩盘；
3. **设计哲学**：拆散传输时只是无符号零件，只有在接收端拼回 16 位后，用 `int16_t` 解释才具备正负号的含义！

```c
// 单片机端 C 语言规范封包实现
uint8_t tx_frame[9];

void Protocol_SendEnvData(float temperature, float humidity) {
    int16_t  temp_fixed = (int16_t)(temperature * 10);
    uint16_t humi_fixed = (uint16_t)(humidity * 10);

    tx_frame[0] = 0xAA; // 帧头1
    tx_frame[1] = 0x55; // 帧头2
    tx_frame[2] = 0x01; // 数据类型: 环境数据
    
    // 网络大端序封包: 先发高 8 位，后发低 8 位
    tx_frame[3] = (uint8_t)(temp_fixed >> 8);
    tx_frame[4] = (uint8_t)(temp_fixed & 0xFF);
    tx_frame[5] = (uint8_t)(humi_fixed >> 8);
    tx_frame[6] = (uint8_t)(humi_fixed & 0xFF);
    
    // 累加和计算
    uint8_t sum = 0;
    for (int i = 2; i <= 6; i++) {
        sum += tx_frame[i];
    }
    tx_frame[7] = sum;
    tx_frame[8] = 0x0D; // 帧尾

    HAL_UART_Transmit(&huart1, tx_frame, 9, 100);
}
```

## 5. Python 上位机多线程与滑窗解包架构

### 5.1 为什么必须采用双线程架构？
如果采用单线程：Matplotlib 图形渲染和坐标重绘耗时较长（30~80ms）。在绘图重绘期间主程序无法读取串口，单片机源源不断发送的数据会将操作系统的串口驱动缓冲区塞爆，抛出 `SerialException: Buffer Overrun` 并造成波形严重断续。

### 5.2 双线程协作与滑窗状态机实现
```python
# 上位机核心解包与状态机逻辑 (截取自 monitor_host.py)
import struct
import threading
from collections import deque
import serial

data_queue = deque(maxlen=200)

def serial_worker_thread(port, baudrate=115200):
    ser = serial.Serial(port, baudrate, timeout=0.5)
    state = "WAIT_HEADER_1"
    
    while True:
        if state == "WAIT_HEADER_1":
            b = ser.read(1)
            if b == b'\xAA':
                state = "WAIT_HEADER_2"
        elif state == "WAIT_HEADER_2":
            b = ser.read(1)
            if b == b'\x55':
                state = "READ_PAYLOAD"
            else:
                state = "WAIT_HEADER_1" # 滑窗回退
        elif state == "READ_PAYLOAD":
            payload = ser.read(7) # 读齐后 7 字节
            if len(payload) == 7:
                # 校验和计算: Byte2 到 Byte6
                checksum = (payload[0] + payload[1] + payload[2] + payload[3] + payload[4]) & 0xFF
                if checksum == payload[5] and payload[6] == 0x0D:
                    # 使用 '>hH' 以网络大端序解码
                    temp_raw, humi_raw = struct.unpack('>hH', payload[1:5])
                    temp = temp_raw / 10.0
                    humi = humi_raw / 10.0
                    data_queue.append((temp, humi))
            state = "WAIT_HEADER_1"
```

## 6. 现场硬件排障实录（高频面试必杀技）

### 踩坑 1：未共地（Missing GND）引发全屏乱码
- **现象**：STM32 板由独立外部适配器供电，USB-TTL 插在电脑上，串口助手上收到的全部是一长串乱码方块字符。
- **根因分析**：电压本质上是两点之间的“电势差”。单片机和电脑 USB 接口之间没有连接 GND 地线，导致单片机的 3.3V 逻辑高电平相对于电脑的地电位在浮动（两者地之间甚至存在几伏的漂移悬空电压），电平门限完全错乱。
- **解决**：飞线将单片机板载 GND 与 USB-TTL 的 GND 牢牢连接，通信波形瞬间变得极其稳定清晰。

### 踩坑 2：RS-232 与 TTL 电平混淆防炸板
- **防范**：老式工业上位机 DB9 串口遵循 RS-232 标准（逻辑 1 为 $-3 \sim -15\text{V}$，逻辑 0 为 $+3 \sim +15\text{V}$）。绝对不能直接把 STM32 引脚插上去，否则十几伏的高压会瞬间击穿芯片内部的 ESD 钳位二极管，必须外挂 MAX3232 转换芯片。

## 7. v2.0 架构瓶颈与演进驱动力

1. **阻塞发送占用 CPU**：`HAL_UART_Transmit` 每次发送耗费 0.78ms，发送频率一旦提高，CPU 将大部分时间空转在串口等待中；
2. **单机任务无法多周期并发**：无法同时满足“高频传感器采集”、“低频屏幕刷新”与“突发通信响应”的不同时序要求；
3. **促使系统演进**：必须引入多任务实时操作系统，迈向 [[03_v3.0_实时操作系统与多传感器融合实录|v3.0 FreeRTOS 阶段]]。
